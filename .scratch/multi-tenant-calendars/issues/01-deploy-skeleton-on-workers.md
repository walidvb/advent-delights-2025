# 01: Deploy skeleton on Workers

**What to build:** The existing single-Calendar site, running as a deployed Cloudflare Worker instead of a static export, with a database and an object store attached and reachable. Nothing about what a visitor sees changes — this ticket exists so that every ticket after it has somewhere to land.

The adapter the project currently deploys with has been deprecated and its repository archived; it is replaced with the supported one. The static-export setting goes with it, since everything after this needs server routes.

**Blocked by:** None (can start immediately)

**Status:** ready-for-human

(Everything an agent can do is done. What remains needs Cloudflare account access:
create the D1 database and R2 bucket, and deploy. See Comments.)

- [x] The upstream project is present locally as this repo's starting commit, with the domain docs already in this directory preserved
- [x] The deprecated deploy adapter and the static-export setting are both gone
- [ ] The app builds and deploys as a Worker and serves the 2025 Calendar exactly as before
- [x] A database binding and an object-store binding are configured and readable from a route, proven by a throwaway endpoint that touches both
- [x] The same works locally against local emulation of both
- [x] Watch for: the Calendar data is read from a spreadsheet file on disk in a server component. That is fine while the page is prerendered at build time, and breaks if it ever renders per request. Confirm which is happening before closing this ticket.

## Comments

### Implementation notes

**Repo setup.** Upstream `walidvb/advent-delights-2025` @ `486f41c` is the starting
commit. The local docs (`AGENTS.md`, `CONTEXT.md`, `docs/`, `.scratch/`, `.claude/`)
were preserved and committed on top as `9fb6dd1`. No filename collided with upstream,
so nothing local was overwritten.

**Adapter swap.**

- Removed `@cloudflare/next-on-pages` (archived) and `output: 'export'` from
  `next.config.ts`.
- Added `@opennextjs/cloudflare` ^1.20.5 plus `open-next.config.ts`.
- `wrangler.jsonc` moved from Pages (`pages_build_output_dir`) to Workers
  (`main` + `assets`), with `DB` (D1) and `BUCKET` (R2) bindings.
- Next bumped `16.0.4` → `16.3.4`: the adapter's peer range is
  `>=15.5.24 <16 || >=16.3.3`, so 16.0.4 is not supported. `eslint-config-next`
  bumped to match.
- `next.config.ts` calls `initOpenNextCloudflareForDev()` so the bindings are
  also present under `next dev`.

**Prerender vs per request — the "Watch for" item, answered.**

The Calendar page (`/`) is **prerendered at build time**. `next build` reports it as
`○ (Static)`, `prerender-manifest.json` gives it `"compute": "static"` with
`"initialRevalidateSeconds": false`, and the 76,430-byte
`.next/server/app/index.html` contains the real CSV data. The `fs.readFileSync` of
`src/data.csv` in `server-tracks.ts` therefore runs on the build machine, not in the
Worker.

That said, this ticket surfaced the exact failure the warning describes. With the
adapter's default (no-op) incremental cache, the Worker had no copy of the
prerendered HTML and re-rendered `/` on every request, which crashed with
`ENOENT: readAll '/src/data.csv'` — `fs` has no `src/data.csv` inside the Worker.
Fixed by configuring `staticAssetsIncrementalCache` in `open-next.config.ts`, which
serves the prerendered page from the Workers assets bundle. Read-only and
non-revalidating, which is exactly right for a page that never revalidates.

Verified: the HTML the Worker serves is **byte-identical** (`cmp`) to
`.next/server/app/index.html` from the build. The visitor sees no change.

This is a landmine for later tickets: once the Calendar renders per request (from
D1 rather than the CSV), the CSV read must be gone or the Worker will crash. Ticket
02 removes it.

**Throwaway endpoint.** `src/app/bindings-check/route.ts` (`force-dynamic`) runs
`select 1` against D1 and does an R2 `put` + `get`. Against local emulation:

```
GET /bindings-check -> 200 {"d1":"ok","r2":"ok 2026-09-01T14:07:33.862Z"}
```

Delete it once real routes use the bindings.

**Incidental fixes, both forced by the adapter swap.**

- `server-tracks.ts`: Cloudflare's runtime types make `Response.json()` return
  `unknown` rather than `any`, so the noembed response needed a cast. Build-blocking.
- `eslint.config.mjs` / `.gitignore`: ignore `.open-next/` and `.wrangler/`.
  Without it `eslint` reported 27,171 problems from build output. The 8 remaining
  problems are all pre-existing upstream code (`DetailsCard.tsx`, `Player.tsx`,
  `VariantSwitch.tsx`) and were left alone.
- `cloudflare-env.d.ts` is generated by `npm run cf-typegen` and committed, so a
  fresh clone type-checks without a wrangler run first.

**Run it locally.**

```
npm install
npm run preview
```

That is `opennextjs-cloudflare build && opennextjs-cloudflare preview` — it builds
the Worker, populates the static-asset cache, and starts wrangler with local D1
and R2 emulation on `http://localhost:8788`. `npm run dev` (plain `next dev`) also
works and also has the bindings.

Both were verified from a clean slate (`rm -rf .open-next .next .wrangler`).

**What was NOT done.**

The "builds and deploys as a Worker" box is unticked because only the *build* half
was proven. `wrangler deploy --dry-run` validates the bundle, the assets directory
and all three bindings, but no real deploy happened: it needs Cloudflare
credentials, a real D1 database (`wrangler d1 create advent` — `wrangler.jsonc`
currently carries `"database_id": "REPLACE_WITH_REAL_D1_ID"`) and a real R2 bucket
(`wrangler r2 bucket create advent-covers`). Publishing was also outside what this
agent may do unattended. Someone with account access needs to create the two
resources, paste the D1 id into `wrangler.jsonc`, run `npm run deploy-app`, and
confirm `/` and `/bindings-check` against the deployed URL.

**Out of scope, untouched, as required.** No player changes, no Track reshaping, no
reveal-rule extraction, no auth, no Calendar/Submission schema.
